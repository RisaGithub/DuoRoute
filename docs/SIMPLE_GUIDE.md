# DuoRoute простыми словами

Этот файл нужен тем, кто впервые открыл проект и не разбирается в платёжных системах.

## Суть за одну минуту

Есть много заявок на выплату денег и несколько сервисов, которые умеют проводить такие выплаты. Эти сервисы отличаются: у каждого свои ограничения, доступная нагрузка, надёжность, стоимость и желаемая доля заявок.

DuoRoute для каждой заявки выбирает подходящий сервис.

Система действует по порядку:

1. Получает список сервисов и очередь заявок.
2. Убирает сервисы, которые точно не могут обработать текущую заявку.
3. Среди оставшихся выбирает наиболее подходящий по выбранной стратегии.
4. Имитирует отправку заявки этому сервису.
5. Если сервис отказал или не ответил вовремя, пробует следующий.
6. Если внешние сервисы не справились, использует резервный сервис `spacepayments`.
7. Сохраняет результат и подробное объяснение каждого решения.

Главная идея: система не просто пишет, куда отправлена заявка, а показывает, **почему выбран именно этот сервис и почему не подошли остальные**.

## Самый простой способ посмотреть проект

Проверьте версию Ruby:

```bash
ruby -v
```

Нужна Ruby `3.4.x`. Затем из корня проекта выполните:

```bash
bin/setup --skip-server
bin/router demo --seed 42
bin/rails server
```

Откройте в браузере <http://localhost:3000>.

Если терминал показывает Ruby `2.6` или ошибку про `Data.define`, значит он запустил старую системную Ruby. Для установленного в проекте `rbenv` обычно достаточно:

```bash
eval "$(rbenv init - zsh)"
rbenv shell 3.4.10
ruby -v
```

После `bin/setup` в системе уже есть демонстрационный запуск. Поэтому знакомство лучше начать со страницы **«Обзор»**, а затем открыть любую операцию из последнего запуска.

## Что находится на каждой странице

| Страница | Что там находится | Что с ней делать |
|---|---|---|
| **Обзор** | Главные цифры последнего запуска, распределение заявок, причины отказов и состояние сервисов | Быстро понять общий результат |
| **Новый запуск** | Загрузка файлов, выбор стратегии и запуск обработки | Загрузить свои данные или использовать уже заполненный пример |
| **Запуски** | История всех запусков | Вернуться к старому результату и сравнить его с новым |
| **Страница запуска** | Прогресс, итоговые показатели, список операций, рекомендации и файлы для скачивания | Посмотреть результат всей очереди |
| **Страница операции** | Полная история выбора одного сервиса: кто не подошёл, кто был выбран и почему | Подробно объяснить одно решение экспертам |
| **Провайдеры** | Все платёжные сервисы, их ограничения, загрузка и доступность | Понять возможности каждого сервиса |
| **Strategy Lab** | Сравнение нескольких способов распределения на одинаковых данных | Показать, как разные приоритеты меняют результат |
| **Аналитика** | Статистика по прошлым операциям, отклонения и рекомендации | Найти слабые места и понять, что можно настроить лучше |
| **Генератор** | Создание обычных, больших и специально проблемных наборов данных | Проверить систему на нагрузке, отказах, тайм-аутах и ошибках |
| **Методология** | Краткое описание правил и формул | Объяснить, как устроен алгоритм |

## Как сделать новый запуск через сайт

1. Нажмите **«Новый запуск»**.
2. Укажите название запуска.
3. Загрузите файлы или оставьте демонстрационные данные, которые уже вставлены в форму.
4. Для первого знакомства оставьте стратегию `balanced`.
5. Оставьте режим тайм-аута `fallback_on_timeout`.
6. Выберите способ имитации результата:
   - `scripted` — заранее заданные ответы; удобен для понятной и повторяемой демонстрации;
   - `seeded` — ответы выглядят случайными, но одинаковый `seed` всегда даёт одинаковый результат.
7. Нажмите **«Запустить маршрутизацию»**.
8. Дождитесь окончания полосы прогресса.
9. Откройте нужную операцию, нажав на её номер в таблице.
10. При необходимости скачайте `Decisions JSON` и `Report JSON`.

Настраивать веса вручную для первого запуска не нужно. Они нужны для экспериментов, когда хочется сильнее учитывать конкретную цель.

## Какие файлы принимает система

- `providers.json` — список сервисов и их возможностей;
- `operations.json` — очередь заявок на выплату;
- `history.csv` — история прошлых выплат, необязательный файл для аналитики;
- routing config в YAML или JSON — настройки и стратегии;
- `outcomes.json` — заранее заданные ответы сервисов для повторяемого теста, необязательный файл.

Файл имеет приоритет над текстом в форме. Перед началом система проверяет все данные. Если в них есть ошибки, она показывает их и не создаёт частичный результат.

## Как выбирается сервис

Сначала действуют обязательные запреты. Сервис исключается, если он, например:

- выключен;
- не принимает такую сумму;
- достиг дневного лимита;
- уже обрабатывает слишком много заявок;
- не работает с нужным банком;
- берёт слишком большую комиссию;
- не имеет свободных реквизитов;
- получает слишком много запросов в минуту.

Только после этого система сравнивает оставшиеся сервисы по желательным целям: соблюдение нужных долей заявок и денег, успешность выплат, свободная нагрузка, скорость, стоимость, подходящий размер выплаты и другие настройки.

Обязательные запреты всегда важнее желательных целей. Нельзя выбрать неподходящий сервис только потому, что у него высокий итоговый балл.

## Что такое стратегии

Стратегия — это набор приоритетов. Она не отключает обязательные проверки, а только меняет выбор среди допустимых сервисов.

- `balanced` — старается разумно учитывать все цели; основной режим для демонстрации и финального запуска;
- `count_share` — сильнее держит нужное распределение по количеству заявок;
- `volume_share` — сильнее держит распределение по сумме денег;
- `cascade` — чаще следует заданному порядку сервисов;
- `conversion_first` — предпочитает сервисы с большей долей успешных выплат;
- `load_safe` — бережёт перегруженные сервисы;
- `turnover_commitment` — помогает выполнить договорённости по денежному обороту;
- `economy_first` — сильнее учитывает выгоду по комиссии.

В **Strategy Lab** несколько стратегий запускаются на одной и той же исходной очереди. Поэтому их можно честно сравнить.

## Что означают основные показатели

- **Approval** — доля заявок, которые завершились успешно;
- **Fallback** — доля заявок, дошедших до резервного `spacepayments`;
- **Latency** — среднее время получения итогового ответа;
- **Цель и факт** — сколько заявок хотели направить сервису и сколько направили на самом деле;
- **Отклонения** — случаи, когда желаемые доли не удалось выдержать;
- **Причины исключений** — какие обязательные ограничения чаще всего мешали сервисам принять заявки.

Отклонение от желаемой доли не всегда является ошибкой. Например, сервис мог быть выключен, перегружен или не принимать нужные суммы. DuoRoute сохраняет это объяснение в отчёте.

## Что особенно полезно открыть внутри одной операции

- **Каскад и fallback** — в каком порядке пробовали сервисы и чем закончилась каждая попытка;
- **Вклад policies** — какие цели увеличили или уменьшили итоговую оценку;
- **Матрица ограничений** — какие обязательные проверки прошёл или не прошёл каждый сервис;
- **State до → после** — как решение изменило дневную сумму, нагрузку и число запросов;
- **Конфликты и tie-break** — как система выбрала победителя, если разные цели предлагали разные варианты.

Это главная страница для объяснения решения на защите.

## Генератор тестовых данных

Генератор помогает проверить не только красивый пример:

- `normal` — обычная работа;
- `hard_limits` — срабатывание обязательных ограничений;
- `fallback` — отказы внешних сервисов и переход на резервный;
- `conflicting_goals` — конфликт разных целей;
- `high_load` — высокая нагрузка;
- `timeouts` — долгие ответы;
- `invalid_data` — намеренно испорченные данные для проверки валидатора;
- `stress` — большой объём данных для проверки скорости.

Можно посмотреть предварительный результат, скачать набор файлов или сразу запустить его.

## Полезные команды CLI

Создать демонстрационный результат:

```bash
bin/router demo --seed 42
```

Проверить входные файлы без запуска:

```bash
bin/router validate \
  --providers data/examples/providers.json \
  --operations data/examples/operations_queue_10.json \
  --config config/routing/default.yml
```

Сравнить стратегии:

```bash
bin/router compare \
  --operations data/examples/operations_queue_10.json \
  --presets balanced,cascade,conversion_first,load_safe
```

Объяснить конкретную операцию из готового результата:

```bash
bin/router explain \
  --decisions routing_decisions.json \
  --operation op_103
```

Посмотреть все команды:

```bash
bin/router help
```

CLI и сайт используют один и тот же алгоритм. Разница только в способе управления и показа результатов.

## Что важно знать перед защитой

- Заявки обрабатываются по очереди, от более ранних к более поздним.
- Каждое новое решение учитывает результат предыдущих заявок.
- Система не заглядывает в будущие заявки.
- Резервный `spacepayments` не соревнуется с остальными: он используется только после внешних сервисов.
- Система не обращается к настоящим платёжным сервисам. Для хакатона их ответы имитируются.
- `seed` нужен для повторяемости: одинаковые входные данные, настройки и `seed` дают одинаковый результат.
- История операций нужна для аналитики. По умолчанию она не меняет обязательные правила маршрутизации.
- Полный ход выбора сохраняется, поэтому любое решение можно воспроизвести и объяснить.

## Короткий сценарий демонстрации

1. На **«Обзоре»** показать главные показатели и распределение заявок.
2. В **«Запусках»** открыть демонстрационный запуск.
3. Открыть операцию `op_103` и показать причины выбора, матрицу ограничений и вклад целей.
4. В **Strategy Lab** сравнить `balanced`, `cascade`, `conversion_first` и `load_safe`.
5. В **«Аналитике»** показать отклонения и рекомендации.
6. В **«Генераторе»** показать сценарий `fallback`, `timeouts` или `invalid_data`.
7. В терминале запустить `bin/router demo --seed 42` и публичный валидатор.

## Финальные конкурсные файлы

Обычные демонстрационные результаты называются:

- `routing_decisions.json` — решение по каждой заявке;
- `routing_report.json` — общая статистика и рекомендации.

Файлы с окончанием `_test` нужно создавать **только после получения настоящего файла `operations_queue_test.json`**:

```bash
bin/router final \
  --operations operations_queue_test.json \
  --providers data/providers.json \
  --config config/routing/final.yml \
  --preset balanced \
  --seed 42
```

Команда сама проверяет вход и создаёт два файла с точными конкурсными именами. Не нужно заранее переименовывать публичные демонстрационные результаты в `_test`.

## Самое короткое объяснение для эксперта

> DuoRoute берёт заявки по одной, отсеивает сервисы, которые не могут провести выплату, выбирает лучший из оставшихся по настраиваемым бизнес-приоритетам и пробует следующий вариант при отказе. Для каждого решения сохраняется полное объяснение, а сайт позволяет увидеть процесс, статистику и сравнение стратегий.
