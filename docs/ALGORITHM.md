<a id="online"></a>
## Последовательная обработка

Online означает, что решение использует только уже обработанную часть очереди. [Engine](../lib/duo_route/engine.rb) сортирует операции по абсолютному времени `created_at`; при равенстве сохраняет входной индекс. Будущие операции не участвуют в выборе. Перед следующей операцией учитывается состояние после предыдущих попыток и синхронных проверок статуса.

Снимок `snapshot_at` задаёт исходное состояние. Операция раньше снимка отклоняется. Входы глубоко копируются; разные Runner не делят изменяемое состояние.

<a id="constraints"></a>
## Обязательные ограничения

Hard constraints — условия допуска, которые нельзя компенсировать высокой оценкой. [Constraints::Registry](../lib/duo_route/constraints/registry.rb) выполняет десять проверок:

| Проверка | Условие допуска |
|---|---|
| Статус | `status == "active"` |
| Минимальная сумма | `amount >= limit_amount_min` |
| Максимальная сумма | `amount <= limit_amount_max` |
| Дневной оборот | `daily_approved_amount + amount <= daily_amount_limit` |
| Число занятых операций | `in_progress_count + 1 <= in_progress_count_limit` |
| Сумма занятых операций | `in_progress_amount + amount <= in_progress_amount_limit` |
| Банк | Пустой banks разрешает любой непустой банк; иначе при exclude_banks=false банк должен входить в список, при true — отсутствовать |
| Маржа | `provider_margin_pct <= merchant_margin_pct`, кроме явного `allow_negative_agreement=true` |
| Реквизиты | `available_requisites > 0`; целое число |
| Интенсивность | Число вызовов в `(created_at−60 секунд, created_at]` плюс новая попытка ≤ requests_per_minute_limit |

Границы включительны. `null` числового лимита означает отсутствие ограничения. Все проверки сохраняются в матрице, даже после первого отказа; `attempts.reason` получает первый код отказа в порядке реестра. Уже превышенные лимиты снимка не обнуляются: кандидат исключается, отчёт объясняет состояние.

<a id="scoring"></a>
## Семь стратегий и комбинированная оценка

Soft goals — цели предпочтения среди допустимых провайдеров. Политика — отдельная формула такой цели. Каждая активная политика возвращает оценку `sᵢ` от 0 до 1; отсутствующее необязательное поле исключает её для этого кандидата, а не даёт нулевую оценку.

`score(p) = Σ(wᵢ × sᵢ(p)) / Σwᵢ`

В знаменателе только веса политик, определённых для кандидата. Нулевой вес полностью исключён, в том числе из разрешения конфликтов; все веса 0 — ошибка конфигурации. Удвоение веса удваивает вклад одинакового изменения нормированной оценки.

Projected означает состояние, которое получилось бы при выборе текущего кандидата. Обозначения: `a` — сумма операции, `Cₚ/C` — число итоговых маршрутов провайдера/всех, `Vₚ/V` — их суммы, `Dₚ` — одобренный дневной оборот. Счётчики C и V относятся только к уже обработанной текущей очереди, включая резерв и неуспешные итоги.

| Стратегия → политика | Формула |
|---|---|
| count_share → CountShare | `projected_pct = (Cₚ+1)/(C+1) × 100`; `s = 1 − abs(projected_pct − traffic_percentage)/100` |
| volume_share → VolumeShare | `projected_pct = (Vₚ+a)/(V+a) × 100`; `s = 1 − abs(projected_pct − volume_share_pct)/100` |
| cascade → Cascade | `s = 1 − (priority − min_priority)/(max_priority − min_priority)` в допустимом пуле; при равных priority — 1 |
| amount_range → PreferredAmount | 1 внутри preferred_amount_min/max; ниже min: `1 − (min−a)/max(min,1)`; выше max: `1 − (a−max)/max(max,1)` |
| conversion → Conversion | `conversion_24h` из снимка или явно включённая калибровка `effective_conversion` |
| intensity → Intensity | `1 − (rpm+1)/requests_per_minute_limit` |
| turnover_commitment → TurnoverCommitment | Для `x=Dₚ+a`: если x < min, `0.7 + 0.3 × (1 − x/max(min,1))`; иначе если x > max, 0; иначе 0.65 |

Все результаты ограничены диапазоном [0,1]. Предпочтительный диапазон суммы и минимальный/максимальный оборот — мягкие цели; они не подменяют обязательные лимиты. В формуле оборота условие недобора min проверяется первым.

Дополнительные факторы комбинации:

- `load_safe`: `1 − max(использование дневного лимита, лимита числа и суммы in-progress)` после добавления операции. Использование — отношение текущей нагрузки к лимиту; отсутствующий лимит не создаёт давления.
- `latency`: `1 − avg_latency_sec/max_latency` допустимого пула; если все времена нулевые — 1.
- `economy`: `(merchant_margin_pct − provider_margin_pct)/merchant_margin_pct`; при нулевой марже мерчанта — 0.

Формулы: [Policies::Registry](../lib/duo_route/policies/registry.rb). Ранжирование: [Scorer](../lib/duo_route/scorer.rb). Каталог семи самостоятельных стратегий: [strategies.yml](../config/routing/strategies.yml).

### Стандартные веса

Balanced: conversion=4; count_share=2; volume_share=2; load_safe=2; intensity=2; turnover_commitment=2; latency=1; economy=0.5. Cascade и preferred_amount выключены в этой комбинации, но доступны отдельно. Seed 42, history включена, minimum_samples=20, calibration.enabled=false.

Это обоснованный baseline — отправная конфигурация; [эксперимент](CRITERIA_COMPLIANCE.md#default) не доказывает глобальный оптимум. Custom задаёт свою комбинацию тех же факторов.

### Конфликты и равенство

Если лучшие кандидаты отдельных политик различаются, сохраняется `policy_winners_disagree`. Решение определяет общий score. При равенстве сравниваются нормированные оценки в порядке `policy_priorities`, затем меньшее `provider.priority`, затем имя `payment_system` по алфавиту. Это tie-break — фиксированное правило равенства. Seed в нём не участвует.

<a id="state"></a>
## Состояние, смена суток и RPM

[State::Store](../lib/duo_route/state/store.rb) принадлежит одному Engine. Перед вызовом `reserve` занимает in-progress count/amount и добавляет время вызова в RPM. При успехе `commit` освобождает резерв и увеличивает `daily_approved_amount`. При отказе `rollback` освобождает резерв, но не отменяет реальный вызов в RPM. Повторный commit без резерва — ошибка; повторный rollback не освобождает чужую исходную занятость.

Даты ISO-8601 обязаны содержать Z/offset; несуществующие календарные даты отклоняются. Сутки определяются в UTC независимо от часового пояса машины. Снимок относится к UTC-дате своего timestamp. При переходе даты сбрасывается только дневной одобренный оборот. Посещённые дни сохраняются в `daily_state_history`; пропущенные не материализуются. Итоговое использование лимита относится к `daily_state_date`.

RPM — реальные запросы текущей очереди в окне `(t−60,t]`: вызов ровно 60 секунд назад уже исключён. Отказ и таймаут тоже считаются. Исторические RPM не восстанавливаются: снимок не содержит списка последних вызовов. Устаревший префикс удаляется бинарным поиском.

Все попытки одной операции относятся к её created_at. Latency суммируется, но не сдвигает время следующей операции. Исходная занятость in-progress остаётся внешней неизвестной нагрузкой до конца расчёта; реальные завершения на границе суток не моделируются.

<a id="cascade"></a>
## Каскад, таймаут и fallback

После обязательных проверок внешние кандидаты ранжируются. Reserve выполняется непосредственно перед вызовом симулятора. `approved` фиксирует успех и завершает выбор; `rejected` освобождает резерв и ведёт к следующему кандидату. Каждый провайдер вызывается максимум один раз на операцию.

При `expired` возможны два режима:

- `fallback_on_timeout` — стандарт по письменному ТЗ: освобождение резерва и следующая попытка.
- `hold_until_status` — удержание до синхронной проверки статуса: поздний approved фиксирует успех, rejected освобождает резерв и продолжает каскад, отсутствующий статус сохраняет резерв и expired. Предыдущие решения не переигрываются.

После исчерпания внешних кандидатов используется fallback — резервный `spacepayments`. Он не участвует в оценке и проходит те же применимые обязательные проверки. Недоступный резерв в строгом режиме останавливает весь расчёт без публикации частичного результата. Его rejected/expired сохраняется как реальный итоговый ответ.

Итоговая selected-попытка ровно одна. `selected_provider` означает конечный маршрут, не гарантию успеха. Только ему добавляются число и сумма в распределение очереди, независимо от статуса. Daily растёт только при approved или подтверждённом позднем успехе. Проверки позднего статуса произвольно после следующих операций не поддержаны.

<a id="simulation"></a>
## Симуляция и история

Вероятностный `Seeded` получает число из SHA-256 строки `seed:operation:provider:attempt`; изменение порядка вызовов генератора случайных чисел не меняет ответы. `Scripted` читает точный ответ для пары операция/провайдер либо общий default. Реальных API нет.

`history` использует частоты approved/rejected/expired из завершённых строк и среднее (`mean`) или медиану (`median`) latency. Учитываются только строки с `created_at + latency_sec <= snapshot_at`. Строка, которая завершится во время очереди, не подмешивается. Дубли и неизвестные провайдеры/статусы отклоняются; cutoff и число отброшенных будущих строк сохраняются в Manifest.

При числе строк меньше minimum_samples=20 или источнике `provider_snapshot`: A=conversion_24h, E=(1−A)×failure_expired_share, R=1−A−E. Здесь A/R/E — вероятности успеха/отказа/таймаута. Стандарт failure_expired_share=0.2; время из avg_latency_sec. Переход к снимку явно отмечается для каждого провайдера.

`custom` задаёт A/R/E с суммой 1 и среднее время ± разброс, минимум 0. Вероятностное время округляется до целых секунд, стандартный разброс 0; scripted допускает конечные неотрицательные дробные секунды. Вероятности задаются долями 0–1, отображаются процентами.

История для симуляции и калибровка конверсии в оценке — разные механизмы. Последняя выключена по умолчанию. При включении и n ≥ minimum_samples:

`effective_conversion = (snapshot_conversion × prior_strength + empirical_conversion × n)/(prior_strength+n)`

Это сглаживание небольшой выборки параметром снимка; стандарт prior_strength=30. История никогда не меняет обязательные ограничения и не добавляется в знаменатель текущего распределения.

<a id="assumptions"></a>
## Денежная точность и трактовки ТЗ

Сравнения и накопления сумм используют BigDecimal без округления до копеек. На границе JSON выдаётся целое либо Float с проверкой обратного преобразования в decimal. Если дробь невозможно передать без потери точности, расчёт выдаёт ошибку. Большие целые поддержаны в конечном числовом диапазоне оценки; NaN/Infinity запрещены. Ограничения отображения JavaScript Number не меняют проверки ядра.

Принятый порядок источников: письменные уточнения организаторов → ТЗ и критерии → публичный валидатор → устный Q&A → примеры формы результата. Уточнение о долях: только текущая очередь и итоговый selected_provider после fallback (Telegram №253, 03.09.2026 22:27:07, зафиксировано в исходной документации проекта).

Нулевая traffic_percentage — мягкая цель, а не запрет. Публичный валидатор трактует её иначе; расхождение указано в [ограничениях проверки](CRITERIA_COMPLIANCE.md#limitations). Сумма долей количества внешних провайдеров должна быть 100% (кроме набора только с резервом); неполные цели объёма допускаются с предупреждением, без молчаливой нормализации.

`latency_sec` обязателен во внутреннем контракте по примеру ТЗ, хотя публичный валидатор его не проверяет. Длительность исполнения программы измеряется отдельно и не является детерминированной частью отчёта; решения воспроизводимы при тех же входах, настройках, seed и версии ядра.

<a id="limitations"></a>
## Недостижимые цели и ограничения

Недоступный провайдер не возвращается в пул ради доли или минимального оборота. Выбирается лучший допустимый вариант; отчёт сохраняет исключения целей и рекомендации. Короткая очередь, разные суммы и конфликтующие цели не позволяют обещать точные доли. Глобальная оптимальность на неизвестном горизонте не гарантирована.

Полное объяснение всей очереди хранится в памяти. Последовательная batch-модель не моделирует одновременные сетевые выплаты и внешние события; состояние не разделяется между рабочими процессами. Для настоящих выплат нужен отдельный адаптер выполнения и сериализации резервов. Условия записи файлов относятся к [архитектуре](ARCHITECTURE.md); проверки и ограничения — к [критериям](CRITERIA_COMPLIANCE.md).


## Наблюдаемая достижимость

`goal_feasibility` строится после последнего решения, по сохранённому допуску каждой операции. Для провайдера: eligible_operations и сумма eligible_amount, цель/факт count-share, частоты всех блокирующих ограничений. Верхний наблюдаемый процент — `eligible_operations / total_operations × 100`. Эти агрегаты никогда не передаются Scorer или State текущей операции.

Если факт совпал с целью, status=`achieved`; если неокруглённый наблюдаемый предел ниже цели — `not_reachable_on_observed_path`; иначе `not_ruled_out`, а `target_reachable_on_observed_path=null`. Последний случай не означает доказанной достижимости: альтернативные назначения меняют лимиты и ответы; дискретность числа операций тоже важна. Это не максимум по всем возможным распределениям.

Рекомендации получают числовые основания допуска. Для цели выше наблюдаемого предела предложение увеличить вес заменяется проверкой блокирующих ограничений и согласованием цели. Counterfactual-пересчёт автоматически не выполняется: большинство советов требует содержательного выбора новой конфигурации.

CLI-сериализация сохраняет проверенную десятичную запись Float через `Float#to_s`: лишний двоичный хвост JSON-генератора не должен превращать собственный результат в неподдерживаемую денежную точность. Это не округляет входную сумму и не ослабляет Money.
