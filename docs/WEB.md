# Web-интерфейс

Web хранит историю расчётов локально и позволяет разобрать каждое решение без чтения JSON. Ответы провайдеров моделируются; реальные выплаты не отправляются.

<a id="start"></a>
## Запуск

Подготовьте Ruby 3.4.10 через rbenv, Bundler и SQLite по [инструкции установки](CLI.md#installation). Из корня проекта:

```bash
bin/setup --skip-server
bin/dev -b 127.0.0.1 -p 3000
```

Откройте <http://localhost:3000>. `bin/setup` устанавливает зависимости, готовит базу и добавляет завершённый публичный пример; повторная подготовка не дублирует его.

При локальной разработке используйте `bin/dev`: он удаляет готовый манифест сборки, чтобы сервер отдавал текущие исходные ресурсы.

```bash
bin/dev -b 127.0.0.1 -p 3000
```

Не запускайте второй сервер на том же порту. После production-сборки выполните `bin/rails assets:clobber`, затем полностью перезапустите сервер через `bin/dev`.

<a id="pages"></a>
## Основные страницы

`ID` в путях — номер сохранённого запуска; `operation_id` — ID из его очереди. Открывайте конкретные записи по ссылкам интерфейса.

| Страница | Откуда данные | Что можно сделать | Что показать организаторам |
|---|---|---|---|
| Обзор `/` | Отчёт выбранного завершённого запуска; без запусков — пустое состояние | Выбрать запуск, посмотреть показатели, доли, ограничения и рекомендации | Цель рядом с фактом и объяснение отклонений |
| Провайдеры `/providers`, `/providers/NAME?run_id=ID` | Снимок провайдеров с настройками и отчёт выбранного запуска | Открыть карточку, сверить лимиты, попытки, оборот и успешность | Почему доступный по сумме провайдер исключён по банку или дневному лимиту |
| Запуски `/runs` | Локальная история `RoutingRun` | Выбрать расчёт по имени, времени и статусу; создать новый | Каждый результат связан со своими входами, стратегией и seed |
| Стратегии `/strategies` | Семь стандартных записей каталога и сохранённые изменения `StrategySetting` | Изменить параметры, восстановить стандартные, перейти к новому запуску и сравнению | Различие самостоятельной стратегии и комбинации |
| Генератор `/generator` | Данные создаются по выбранному сценарию и seed | Предпросмотр, скачать набор, сразу запустить | Сценарий отказов или некорректных данных |
| Новый запуск `/runs/new` | Публичные входы по умолчанию, затем загруженные файлы | Настроить очередь, стратегию, симуляцию, seed | Валидация до начала расчёта |
| Запуск `/runs/ID` | Сохранённые входы, прогресс, решения и отчёт этой записи | Следить за статусом, читать рекомендации, открыть операцию, просмотреть/скачать файлы | Decisions, Report, Config и Manifest одного расчёта |
| Операция `/runs/ID/operations/operation_id` | Операция и полное объяснение из сохранённого запуска | Разобрать попытки, ограничения, оценки и состояние; посмотреть JSON | Причина выбранного маршрута и каждого исключения |
| О продукте `/about` | Описание процесса, каталог стратегий, публичные примеры, пять документов из репозитория | Перейти в новый запуск, скопировать CLI-команды, открыть документацию | Как CLI и Web используют одну реализацию |

Документы на `/about/docs/cli`, `/about/docs/web`, `/about/docs/criteria_compliance`, `/about/docs/architecture`, `/about/docs/algorithm` показываются как экранированный исходный Markdown. Для переходов по внутренним ссылкам удобнее открыть документы в репозитории.

<a id="new-run"></a>
## Создание запуска

1. Откройте «Новый запуск».
2. Используйте подставленный публичный пример или загрузите свои providers, operations, config; при необходимости history и outcomes. Поля исходных данных доступны только для чтения.
3. Выберите одну из семи стратегий, balanced или custom.
4. Проверьте параметры стратегии, YAML/JSON и строки `path=value`. Веса формы применяются только с флажком переопределения.
5. Выберите источник симуляции: history, provider_snapshot, custom или scripted. Для scripted загрузите outcomes.
6. Укажите неотрицательный целый seed, например 42. Для сравнения сохраняйте его одинаковым.
7. Запустите расчёт. Ошибки показываются с полем/строкой до создания задания.
8. Дождитесь `completed`. Страница опрашивает прогресс; при `failed` показывает сообщение об ошибке.
9. Скачайте Decisions и Report; для повторения также Config, Manifest и входы.

**Загруженный файл заменяет соответствующий публичный пример для этого запуска.** Поля предпросмотра не редактируются. Чтобы вернуться к примеру, удалите выбранный файл. Настройки меняются через поля стратегии, веса, `path=value` или загруженный Config. После ошибки валидации исходные поля снова показывают публичный пример; исправленный файл нужно выбрать повторно. History/outcomes необязательны в обычных режимах.

Порядок настроек: общие значения → выбранная стратегия (включая сохранённые параметры) → пользовательский config → `path=value` → включённые веса и явные поля формы (источник, timeout, seed). Выбор стратегии применяет только явно сохранённые параметры; несохранённые примеры каталога не становятся входными целями. Сервер выполняет ту же подготовку и без JavaScript.

Готовая запись хранит собственные входы и конфигурацию. Изменение стратегии в каталоге не пересчитывает старые результаты. Запуск повторной доставки задания для completed-записи не меняет результат. Отмены задания в интерфейсе нет; очередь выполняется последовательно в процессе сервера.

<a id="overview"></a>
## Обзор и показатели

Выберите запуск в списке. Ссылка получает `?run_id=ID`, выбор можно передать другому проверяющему. По умолчанию используется последний успешно завершённый запуск по времени завершения: у него уже есть полный отчёт. Незавершённые записи не смешиваются со статистикой.

Цели берутся из снимка провайдеров **после применения настроек этого запуска**. Факты — из его итоговых решений, не из всех записей базы. История используется отдельно для анализа и симуляции.

| Показатель | Значение |
|---|---|
| Approval | Доля операций с итоговым `approved` |
| Reject | Доля операций с итоговым `rejected` |
| Expired | Доля операций с итоговым `expired`, когда итоговый статус не разрешён |
| Fallback | Доля операций, ушедших на резервный spacepayments |
| Latency | Средняя сумма времени всех фактических попыток одной операции, включая неудачные |
| Доля количества | Число операций итогового провайдера / число операций очереди × 100% |
| Доля объёма | Сумма операций итогового провайдера / сумма всей очереди × 100% |
| Отклонение | Факт минус цель, в процентных пунктах |

Итоговый маршрут учитывается и при неуспешном результате. История не добавляется в знаменатель. Отказы промежуточных попыток могут быть даже при итоговом Approval 100%.

Отклонение от цели не всегда ошибка: обязательные лимиты и банковские фильтры важнее долей; небольшая очередь дискретна, суммы различаются, несколько целей могут конфликтовать. Смотрите причины исключений, `target_exceptions` и рекомендации с числовым основанием. Недостижимый оборот нельзя обеспечить только увеличением веса.

<a id="providers"></a>
## Провайдеры

Страница относится к выбранному запуску. Исходные параметры взяты из его Providers с применёнными изменениями; фактическая работа — из отчёта. При отсутствии завершённого запуска показывается пустое состояние.

| Поле/блок | Как читать |
|---|---|
| Daily | Одобренный оборот текущих суток UTC: стартовый снимок плюс успехи очереди; при смене даты сбрасывается |
| Дневной лимит | `daily_amount_limit`; сумма следующей операции тоже должна помещаться |
| Загрузка | Число и сумма in-progress — зарезервированных операций; исходная занятость снимка сохраняется |
| Лимиты in-progress | Ограничивают projected состояние, то есть состояние с учётом новой попытки |
| Конверсия | `conversion_24h` — параметр ожидаемой успешности; фактический Approval провайдера считается по его попыткам |
| Latency | Параметр `avg_latency_sec` отдельно от среднего времени реальных моделируемых попыток провайдера |
| Банки | Пустой список разрешает любой непустой банк; include допускает перечисленные; exclude запрещает перечисленные |
| Реквизиты | `available_requisites > 0` для допуска; расход отдельных реквизитов не моделируется |
| Маржа | Стоимость провайдера не выше маржи мерчанта, кроме явного `allow_negative_agreement=true` |
| RPM | Реальные запросы за последние 60 секунд; отказы тоже расходуют интенсивность |
| Причины исключений | Коды обязательных проверок и их частота; подробности — в операции |

`spacepayments` — резервный провайдер. Он не соревнуется по оценке с внешними, вызывается после их исчерпания, но проходит те же обязательные проверки. Недоступный резерв останавливает расчёт; его выбор не гарантирует успех.

<a id="strategies"></a>
## Стратегии

Семь карточек: `count_share`, `volume_share`, `cascade`, `amount_range`, `conversion`, `intensity`, `turnover_commitment`. Названия и стандартные параметры загружаются из `config/routing/strategies.yml`. Значения и смысл — в [CLI](CLI.md#settings), формулы — в [алгоритме](ALGORITHM.md#scoring).

На странице можно сохранить изменения параметров провайдеров для конкретной стратегии или восстановить стандартные. Сохранённые параметры находятся локально в `StrategySetting`; в новом запуске они становятся отправной точкой. «Сохранить» записывает параметры, «Сбросить» восстанавливает стандартные, «Новый запуск ↗» открывает форму расчёта. CLI не читает Web-базу: для точного повторения скачайте Config и входы.

`balanced` — готовая комбинация; `custom` — собственные веса. Они выбираются в форме нового запуска, не увеличивая число семи карточек. Дополнительные факторы: загрузка `load_safe`, время `latency`, экономика `economy`.

Чтобы создать пользовательскую конфигурацию, откройте «Новый запуск», выберите «Полностью пользовательская настройка», раскройте «Расширенные параметры» и включите «Переопределить preset этими весами». Задайте неотрицательные веса существующих политик; хотя бы один должен быть положительным. Нажмите «Запустить маршрутизацию». В результате скачайте Config для повторного использования через поле «Config YAML / JSON» или CLI `--config`. Отдельного каталога именованных пользовательских стратегий в Web нет; семь встроенных стратегий остаются доступны.

Сравнение `/strategies/compare` использует **публичные 10 операций и одинаковый исходный снимок**, а не произвольный выбранный запуск. Можно выбрать минимум две стратегии, seed, стандартные или сохранённые настройки. Симуляция сравнения — `provider_snapshot`. Для каждой стратегии состояние начинается заново. Это позволяет сравнить влияние правил при одинаковых условиях; показатели являются моделированием. Сортировка: выше Approval, ниже Fallback, ниже Latency, затем имя. Сравнение своей очереди выполняется через `bin/router compare`.

<a id="operation"></a>
## Страница операции

Читайте сверху вниз:

1. Итоговый провайдер и результат. Выбор маршрута и успех выплаты — разные сведения.
2. Попытки: кто исключён до вызова, кого вызвали, какой ответ и время получены. Каскад — переход к следующему кандидату после отказа; fallback — переход к резервному spacepayments.
3. Hard constraints — обязательные ограничения. Матрица показывает все проверки, фактическое значение, границу и причину; высокий score не отменяет запрет.
4. Score — оценка допустимого кандидата от 0 до 1. Разбор показывает значение цели, её вес и вклад в итоговую оценку. Рейтинг сравнивает только допустимых внешних провайдеров.
5. Конфликт целей и tie-break — правило выбора при равной оценке: значения политик в заданном порядке → приоритет провайдера → имя. Seed здесь не используется.
6. State до и после — оборот, занятая ёмкость и RPM. Reserve резервирует ёмкость перед попыткой, commit фиксирует успех, rollback освобождает резерв при отказе.
7. Исходный JSON — полное сохранённое объяснение для сверки с CLI `explain`.

Для публичного demo удобны `op_103` (ограничения суммы) и `op_101` (три отказа и fallback). Для других запусков выбирайте операцию с фактическими отказами по её таблице.

<a id="generator"></a>
## Генератор

Задайте сценарий, количество операций 1–20 000, число внешних провайдеров 1–50 и seed ≥ 0.

| Сценарий | Что проверяет |
|---|---|
| `normal` | Обычное распределение на доступных провайдерах |
| `hard_limits` | Ограничения суммы, ёмкости и допуска |
| `fallback` | Исчерпание внешних вариантов и резерв |
| `conflicting_goals` | Несогласованные цели количества, суммы и оборота |
| `high_load` | Высокую исходную загрузку |
| `timeouts` | Истечение ожидания и переходы |
| `invalid_data` | Ошибочные входы и понятные сообщения валидации |
| `stress` | Большую очередь; для 50k используйте CLI |

Preview показывает состав и примеры без сохранения запуска. Download скачивает единый `duoroute_SCENARIO_bundle.json` с providers, operations, outcomes, history и manifest; это **не** готовый файл очереди. CLI-генератор сохраняет компоненты отдельно.

«Запустить» проверяет набор и создаёт запуск со стратегией по умолчанию с точными scripted-ответами. `invalid_data` ожидаемо отклоняется, а не создаёт успешный расчёт. История набора сохраняется; ответы непосредственного запуска задаёт outcomes.

<a id="security"></a>
## Безопасность

Upload и каждое текстовое поле ограничены 10 MiB. YAML читается безопасным `safe_load` без объектов и ссылок. Входные тексты и реквизиты фильтруются в логах, телефоны маскируются на страницах; скачанные исходные данные могут содержать полные реквизиты.

Ресурсы интерфейса, включая Chart.js, локальные: CDN и телеметрии нет. Расчёты и история хранятся в локальной SQLite. Документы и скачивания выбираются из фиксированного списка, URL не даёт открыть произвольный файл. Пользовательской авторизации нет; сервер разработки предназначен для локального использования. Подробнее — [безопасность и ограничения](CRITERIA_COMPLIANCE.md#security).

## Проверить за 3 минуты

На `/about` доступны копируемые команды readiness, demo и rehearse-final, ссылка на актуальный завершённый запуск, операции с hard exclusions и cascade/fallback, сравнение стратегий и критерии. ID не зашиты в шаблон. Если запусков нет, отображается действие создания примера.

На странице нового результата и «Обзоре» показана достижимость целей: цель, факт, число/сумма допущенных операций, наблюдаемый предел и причины отклонений. Старые сохранённые отчёты не пересчитываются и могут не иметь этого раздела. `not_ruled_out` означает отсутствие доказанной невозможности по наблюдениям, а не гарантию достижения.

Для проверки рекомендаций создайте запуск с изменёнными параметрами и сравните результаты на одинаковых входах.



## Результаты и сравнение

На странице операции отдельно подписаны первоначальный кандидат (первый реальный вызов) и итоговый selected_provider после каскада. Timeline сохраняет все attempts: hard exclusions, rejected/expired с причиной перехода, следующий вызов и конечный результат. Fallback отображается как итоговый маршрут, если внешние кандидаты исчерпаны; report учитывает операцию у него.

Отсутствующая цель объёма отображается как «не задано», в JSON остаётся null. При частичных целях отклонение считается только для заданных провайдеров, их имена перечислены рядом. Явный 0 — действующая цель. Форма volume_share разрешает пустые поля. Графики не подменяют null нулевой целью.

Сравнение на странице стратегий использует один snapshot и одинаковые цели/лимиты для всех кандидатов. Источник «По умолчанию» читает входной snapshot; «Сохранённые» применяет объединение явно сохранённых настроек ко всем стратегиям. CLI compare также не меняет цели при смене стратегии. Лидер Web определяется только по approval, fallback и latency, поэтому его нельзя объявлять лучшим по распределению. Default — `balanced`, версия `paired-final-v1-2026-09-06`. Balanced — единственный проверенный статический кандидат с worst-case regret успешности не выше 0,1 п.п. и на validation, и на holdout. Кандидат `amount_range` имеет больший worst-case regret на holdout. Глобальная оптимальность не доказана. Auto не включён.

На странице «О продукте» объяснено: reference mismatch отражает конфликт статического первоначального выбора с итоговым каскадом, а semantic audit проверяет корректность самого маршрута. Строгая репетиция возвращает ошибку без явного --allow-reference-mismatch. Полного математического оптимума приложение не обещает.
